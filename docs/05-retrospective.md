# 项目复盘

## 1. 个人主导的思路

我把项目的目标放在“可查证地回答”，而不只是生成一句看起来合理的答案。先明确业务范围与完成标准，再建立项目骨架，最后实现模型决策、证据引用、错误处理和验证材料。

设计时重点保留模型可替换、离线与真实效果分开、冲突继续查证、故障有明确状态、隐私不进入公开材料等原则。AI按方案实现代码并提供部分局部建议，我负责取舍、检查与反馈。

## 2. 人工体验带来的优化

完成实现后，我人工检查测试用例，并手动模拟普通用户问答。实际使用提醒我：命令能执行，不代表第一次使用的人就知道怎样执行；程序有状态字段，也不代表用户能够理解当前还缺少什么。

因此补充分步操作、正常与冲突结果示例、引用和状态说明，并把能力证据集中组织。人工操作摘要见 [人工检查记录](09-manual-validation.md)。

## 3. 最难的问题

最难的是让回答内容、运行机制和验证材料保持一致。原文引用、真实模型决策、受限环境的网络与文件行为是不同层面，任何一层都不能由一个成功示例替代。

Windows与Linux的进程回收方式不同，故障注入也必须只影响目标边界；否则测试可能破坏自己正在验证的清理过程。真实模型接入中，CLI诊断和工具事件需要分开判断，同时仍要确认成功终态和有效决策。

预算边界也需要单独测试：没有额度继续读取，不等于知识库没有资料。把执行失败、资料缺口和制度冲突分清楚，才能让结果状态对使用者有意义。

## 4. 学习与改进

- 检索到一个正确来源，并不代表已经排除冲突。同主题来源提示和补充检索有助于比较竞争制度。
- 原文由运行时组装可以减少伪造引用，但结论能否由原文支持仍需要语义检查。
- 超时和取消必须覆盖外部进程，不能只限制循环次数。
- 恶意内容要实际进入观察，负向测试才有意义。
- 技术组件应由失败和收益证据驱动；小型资料不必先引入复杂平台。
- 使用体验需要人工参与，分步说明和清楚的结果解释也是工程质量的一部分。

## 5. 后续工作

目前验证基于小型合成资料和有限真实调用。下一步应增加不同表达、适用范围、例外与多轮追问样本，持续记录人工反馈，并引入独立第三方业务核对。

只有出现真实服务消费方时，再扩展身份认证、服务端访问策略、资料保留策略和容量验证。长文档接入、企业同步及线上可用性仍需独立设计与验证。当前结果与限制见 [评估](03-evaluation.md)。
