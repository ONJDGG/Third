# 个人贡献与 AI 协作

我负责项目的总体方案、实现边界、工程质量标准和结果判断，并在完成后人工检查测试用例、手动模拟用户问答，根据体验提出优化建议。AI主要承担代码编写与具体实现，提供部分技术建议；方案选择、检查重点和优化取舍由我把关。

## 1. 方案与技术决策

| 个人负责的事项 | 形成的设计或要求 | 可核对材料 |
| --- | --- | --- |

| 划分模块与实现顺序 | 先完成骨架、协议和工具，再填充决策循环、模型适配与验证 | [开发计划](../DEVELOPMENT_PLAN.md) |
| 设计模型接入边界 | 统一接口，允许选择模型或Mock，业务逻辑不依赖单一供应商 | [方案](02-solution.md)、src/providers/ |

## 2. 人工检查与反馈

我已经人工检查测试用例，并从普通使用者视角手动模拟了问答过程。检查不仅看能否输出答案，也关注答案是否带出处、结果状态是否容易理解、需要补充条件时是否知道下一步如何操作。

体验过程中提出的明确反馈包括：操作命令需要分步骤说明，不能要求用户一次处理一整段命令；正常回答、冲突和资料不足应有易理解的说明。相应调整已反映在README、运行手册与能力验收文档中。

人工检查以摘要形式记录，见 [人工检查与问答体验](09-manual-validation.md)。现有AI语义复核JSON继续保留原始来源；手工活动没有另行生成逐条终端日志或统计通过率。

## 3. AI使用范围

AI主要用于按确认的方案编写代码、生成模块骨架、实现工具与模型适配、补充测试和脚本，以及执行验证命令和具体排障。对于局部实现，AI提供备选建议，再由我结合业务目标与工程要求作出选择。

AI也辅助整理技术说明与测试报告。代码输出、运行记录和复核记录按各自来源保存，便于复现和检查。

## 4. 错误检查与工程改进

| 检查中暴露的问题 | 处理方式 | 验证方式 |
| --- | --- | --- |
| Windows受管环境拒绝硬链接 | 使用平台适配的原子无覆盖保存 | 旧结果不可被覆盖的回归 |
| 临时目录与网络环境不兼容 | 隔离临时文件，显式检查进程网络配置 | 干净环境与真实调用 |
| JSON正常转换被误判为脱敏 | 比较规范化后的JSON内容 | 业务场景与脱敏检查 |
| CLI诊断事件被误判为工具执行 | 区分诊断与实际工具事件，仍检查成功终态 | 适配器正向与负向测试 |
| 低预算被误报为资料不足 | 状态必须有观察依据，预算耗尽优先返回未完成 | 新增回归及真实预算运行 |
| Linux取消测试受全局替换影响 | 将故障注入限制到项目自己的等待函数 | 四组跨平台CI |

这些问题形成了“检查—定位—修改—复验”的闭环。具体修复由AI辅助实现，我负责检查标准与最终方案把关。详细失败和重跑记录见评估文档。

## 5. 验证与资料管理

自动测试检查可执行约束，真实模型运行验证动态决策，作者人工检查补充使用体验，AI辅助复核帮助逐项比较答案与原文。各类记录分开管理，当前尚未开展独立第三方审计或大规模线上验证。

公开材料使用合成制度和合成问题，不包含账号凭证、私有配置、代理地址或原始CLI会话流。模型、工具和验证的适用边界见 [方案](02-solution.md) 与 [评估](03-evaluation.md)。
